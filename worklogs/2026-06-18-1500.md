# 2026-06-18 - IP-Based Authentication System Implementation

**Duration**: Session

**Objective**: Design and implement a flexible IP-based access control system to complement existing API key authentication, supporting reverse proxies (Koyeb) with customizable IP whitelists for admin endpoints and sensitive data mutations.

## Key Points

- Created comprehensive IP-based authentication middleware system with reverse proxy support
- Implemented IP extraction from direct connections and `X-Forwarded-For` headers (Koyeb-compatible)
- Protected all admin endpoints (`/api/admin/*`) and sensitive data mutations (POST/PUT/DELETE on `/api/people`)
- Designed two-layer authentication: IP whitelist check (403) followed by API key validation (401)
- Environment variable driven (`ADMIN_ALLOWED_IPS`) with graceful fallback when not configured
- Followed existing Express middleware patterns for consistency and maintainability
- Secured previously unprotected people write endpoints

## Decisions Made

1. **IP validation first** - IP check happens before API key check for faster rejection of untrusted IPs
2. **Protect people mutations** - All write operations on `/api/people` now require authentication (were previously dangerously open)
3. **Distinct HTTP status codes** - 403 Forbidden for IP denials, 401 Unauthorized for invalid API keys (helps with debugging)
4. **Comma-separated format** - Simple environment variable format without dependencies
5. **Graceful degradation** - If `ADMIN_ALLOWED_IPS` not set, IP validation is skipped (backward compatible for local development)
6. **X-Forwarded-For support** - Extracts real client IP from proxy headers (critical for Koyeb)

## Notes

- The system handles both direct connections (`req.ip`) and proxied requests (`X-Forwarded-For` header)
- Local development: Set `ADMIN_ALLOWED_IPS=127.0.0.1,::1` for IPv4 and IPv6 loopback
- Koyeb automatically adds `X-Forwarded-For` header; no additional proxy configuration needed
- IP whitelists are environment variable based (static, reproducible across deployments)
- All authentication failures are logged for security auditing
- Future enhancement: Support CIDR notation (e.g., `192.168.1.0/24`) or database-driven dynamic whitelists
